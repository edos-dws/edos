# CP-10 Report — Project & Conversation model

**Status:** ✅ Complete · **Branch:** `cp-10` → `develop` · **Gate:** self-merge (low risk)

## What was built
Foundation for the stateful platform: projects, conversations, and turns — so a user can chat *within a
project* and every exchange is recorded and linked.

- **DB models** (`src/edos/db/models.py`): `ConversationRow` (id, project_id, title, created_at),
  `TurnRow` (id, conversation_id, prompt, response_json, decision_id, created_at). `ProjectRow` already existed.
- **Alembic** (`alembic/versions/0002_conversations_turns.py`): incremental migration on top of 0001.
- **Store layer** (`src/edos/store/projects.py`): pure data-access CRUD — projects (create/get/list/update/
  delete with cascade), conversations (create/get/list), turns (add/list), and the **context-link hook**
  `project_for_conversation()` that CP-13 retrieval will use to scope context to a project.
- **Session dependency** (`src/edos/api/deps.py`): lazy engine/session factory; `get_session` yields a
  request-scoped session (commit on success, rollback on error). Importing the app never needs a live DB.
- **REST endpoints** (`src/edos/api/app.py`):
  - `POST/GET/PATCH/DELETE /v1/projects`, `GET /v1/projects/{id}`
  - `POST/GET /v1/projects/{id}/conversations`, `GET /v1/conversations/{id}` (with turns)
  - `/v1/analyze` now accepts optional `conversation_id`; when set, the exchange is recorded as a turn
    (stateless path unchanged when absent).

## Design notes / alignment
- Store = pure data access (no reasoning) — keeps engine responsibilities clean (CLAUDE.md invariant).
- Ids generated by the API (`uuid4[:12]`); store stays deterministic (caller supplies id) for testability.
- Backward compatible: `/v1/analyze` without `conversation_id` behaves exactly as before (no DB dependency).
